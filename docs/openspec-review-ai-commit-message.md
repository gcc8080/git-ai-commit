## 2. 建议保留的核心设计

整体架构有合理基础，无需推倒重做：

- 通过 `prepare-commit-msg` 填入草稿，保留人工审阅；显式消息、特殊 Git 操作和取消行为单独处理。
- 从有效 index 取得不可变 tree，再围绕 base/target tree 采集变化，避免普通暂存、部分暂存和临时 index 混淆。
- 后端传输解析、候选 schema 校验和本地渲染分层，统一生成 breaking-change 标记，保留用户尾注。
- 核心同步路径与预热缓存解耦；缓存失效只影响速度，不应改变提交内容。
- Git 子进程与模型子进程分别处理环境，失败诊断不直接回显原始 diff，不在 hook 内登录。

主要工作是把这些原则落实为一致、可验证的行为契约。

## 4. 详细意见

### R01 — `post-index-change` 参数语义需要纠正

**依据**：[design D3][design]（L75–97）把 `$2` 定义为“索引被更新”，据此认为 `[ "$2" = 1 ]` 可以精确选出 `git add`。[预热规格][cache-spec]（L10–25）又将触发能力扩展到 IDE、终端 UI 和 agent 的暂存操作。

**核实结果**：官方文档把第二个参数与 index 更新且 skip-worktree 位可能变化关联；Git v2.50.1 的实现传入的是 `istate->updated_skipworktree`。因此不能把它定义成通用的“暂存内容变化标志”，也不能由一次本机触发矩阵推导所有客户端和命令都被覆盖。来源：[官方 hook 文档](https://git-scm.com/docs/githooks#_post_index_change)、[v2.50.1 read-cache.c](https://github.com/git/git/blob/v2.50.1/read-cache.c#L3154)。

这不等于已经证明当前机器上的普通 `git add` 会漏触发；已证实的是设计对参数语义的解释不准确，完整覆盖仍待验证。切换分支、reset、stash 也不能笼统称为“不更新索引的操作”。

**影响**：缓存去重只能抑制收到信号后的重复生成，不能弥补没有收到信号的漏触发。GUI 是否调用原生 Git、是否执行该 hook，也需要成为支持条件。

**建议**：将 hook 定义为可能的预热提示；收到提示后仍依据 tree、操作状态与缓存决定是否生成。若保留 `$2` 守卫，应标为经过支持矩阵验证的优化，明确漏触发时回到同步生成，不宣称覆盖一切暂存方式。

**验收**：在支持的 Git 版本上覆盖新增、修改、删除、`add -p`、取消暂存、切换分支、稀疏检出及已声明支持的 GUI；证明不会使用错误快照，并记录哪些操作只保证同步路径可用。

### R02 — Fallback 的默认策略存在直接冲突

**依据**：[design D8][design]（L185–190）默认开启回退链；[后端规格][adapter-spec]（L108–120）要求回退链必须由用户显式配置。

**影响**：相同输入可能被发送给用户没有选定的第二个服务。另一实现者也可能依据规格关闭 fallback，形成与设计相反的默认行为。

**建议**：保留“支持 fallback”的能力，默认使用一个选定 profile；仅启用用户在本机明确配置的回退链。安装时可以提供推荐配置，但不能根据已安装 CLI 自动授权跨服务发送。额度耗尽、网络错误、认证失败、参数错误和用户取消应分别定义是否允许回退。

还需区分 harness 多样性与供应商/账户多样性：原设计已说明 codex 与 pi 可能共享同一份额度，切换 CLI 未必能恢复可用性。

**验收**：没有回退配置时第二后端调用次数为零；已配置时最多切换一次；配置错误和用户取消不触发回退；所有调用共用同一总截止时间。

### R03 — Fail-open 应写成明确的条件规则

**依据**：[Git 接入规格][git-spec]（L94–111）先规定任何后端故障都不得阻塞提交，随后要求无编辑步骤时生成失败必须中止。[生成规格][generation-spec]（L116–127）还要求重复快照失效时中止。[design Goals][design]（L45–49）仍使用无条件“不阻塞”的表述。

**影响**：实现无法同时满足上位要求和例外场景；用户取消可能被错误当作普通失败放行，或者显式提供消息的提交被无编辑器规则误拦截。

**建议**：按下表统一 proposal、design 和 spec，并明确先判断是否需要生成，再进入生成失败处理。

| 场景 | 建议行为 |
| --- | --- |
| 显式消息、特殊操作或启用单次跳过 | 不进入生成流程，保留 Git 原有行为 |
| 需要生成，有编辑步骤，后端失败 | 原消息文件不变，简短诊断后交给编辑器 |
| 需要生成，无编辑步骤，生成失败 | 中止提交，提示补充消息或恢复编辑步骤 |
| 用户主动取消 | 取消本次提交，不自动重试或切换后端 |
| 快照持续变化或严格检查失败 | 中止并保留用户文字，说明需要重新确认内容 |

Git 会在明确不启动编辑器的提交 hook 环境中设置 `GIT_EDITOR=:`，可作为已知信号；不要把“某个自定义编辑器最终没有修改消息”也承诺为可提前识别的情况。来源：[Git hook 文档](https://git-scm.com/docs/githooks#_pre_commit)。

**验收**：覆盖 `-m`、`-F`、`-s`、普通编辑、`--no-edit`、跳过开关、取消和连续快照变化；逐项断言退出码与消息文件是否修改。

### R04 — 明确严格一致性检查是否属于第一版

**依据**：[proposal][proposal]（L19–22）只安装两个 hook；[design][design]（L250–252）依赖 `commit-msg` 做编辑后复核；[生成规格][generation-spec]（L125–127）则把它写为“启用了严格一致性检查”时的条件行为。

**影响**：当前安装范围无法完整交付该场景，且严格模式没有配置项、默认值、跨 hook 状态传递或卸载定义。

**建议**：若第一版保留该能力，把 `commit-msg` 明确列为严格模式的第三个 hook，并定义 worktree 内的本次调用标识、预期 HEAD/target tree、有效期和清理规则。没有本次生成记录时应跳过检查，避免一次失败或取消遗留的记录误伤后续 `-m` 提交。

检查应位于已知会修改 index 的 hook 逻辑之后；只检查和中止，不覆盖用户编辑结果。Git 允许 `--no-verify` 跳过 `commit-msg`，因此不能把这种复核承诺为不可绕过、没有时间窗口的原子保证。来源：[Git commit-msg 文档](https://git-scm.com/docs/githooks#_commit_msg)。

另一种可接受选择是第一版不交付严格模式，并把相应场景明确移出本次变更。单纯把第三个 hook 留在风险段落中不够。

**验收**：编辑前后改变 index、检查链内重新暂存、取消后下一次提交、`--no-verify`、worktree 隔离都有确定行为。普通提交、`-a` 和路径提交应分别与最终 commit tree 做对照验证。

### R05 — 后端隔离要求需要逐项证明

**依据**：[后端规格][adapter-spec]（L10–35）要求运行环境阻止仓库写入，并关闭工具、扩展、上下文发现、外部工具协议和会话持久化；[design][design]（L18–23、L217–225）目前只列出部分参数。其中 opencode 的“独立运行”没有说明如何实现“不落 session”。

**影响**：临时工作目录和清理 Git 环境变量本身不会撤销同一操作系统用户的文件权限；工具权限禁止也不自动证明插件初始化或生命周期 hook 不会执行。必须区分可信 CLI 的受限调用与操作系统级隔离保证。

**建议**：增加按“后端 + 支持版本”维护的能力矩阵，逐项列明：参数、是否需要隔离用户配置、认证如何复用、是否启动插件/MCP、是否保存 session，以及如何验证。缺少必需限制的版本应判定不兼容，延续当前规格中的保守行为。

不要过早规定“不得存在 per-harness 模块”。通用进程执行器和几种结果解析器值得共享，但探测、参数映射、错误分类及安全设置允许有小型专用适配逻辑。最终验收应约束行为，而不是限制源文件布局。

**验收**：在受控测试配置中启用可观测的扩展、上下文文件、MCP 和会话记录，逐后端验证限制确实生效；截断事件流、非零退出、超时及子进程存活均按失败处理。本次评审未完成这些真实后端验证。

### R06 — 预热应有独立的启用与发送语义

**依据**：[proposal][proposal]（L20–22）和[预热规格][cache-spec]（L10–38）在暂存时启动后台生成；[Git 接入规格][git-spec]（L19–21、L113–120）又要求显式消息和单次跳过时不调用模型。

**影响**：用户执行 `git add` 后，即使下一步用 `git commit -m`、启用跳过开关或最终不提交，后台请求也可能已经发生。提交阶段的跳过无法撤回此前发送的数据。预热还可能出现在特殊 Git 流程的暂存操作中。

**建议**：将“commit 阶段不发起生成”和“整个工作流从未发送数据”分开定义。预热应有本机/仓库本地开关，首次启用时说明发送发生在暂存阶段；默认关闭是本报告的产品建议，并非现有规格已经确定的结论。不得由仓库共享格式配置静默开启额外发送。

还应明确后台是否允许 fallback、如何记录简短状态，以及 merge/rebase 等流程的预热策略。后台静默要求与 fallback 诊断要求可由调用入口分别处理，无需把原始后端输出写入终端。

**验收**：预热关闭时，单独暂存的后端调用次数为零；开启后 `add → commit -m` 的发送行为与说明一致；commit 跳过不会新增请求，但也不会被描述成能撤回已完成的预热。

### R07 — 统一后台与前台生成的任务生命周期

**依据**：[预热规格][cache-spec]（L58–65）规定同 key 正在生成时去重；L85–87 又要求预热未完成时前台独立同步生成；L102–108 要求刷新后覆盖缓存。[design][design]（L246–247）明确接受连续暂存产生多次请求。

**影响**：现有去重只覆盖后台入口，不覆盖前后台重复请求。较慢的旧预热也可能在强制刷新完成后覆盖新结果。失效锁、孤儿进程和不同 tree 的并行任务尚无规则。

**建议**：定义每个 key 的 `absent / running / ready / failed` 状态及原子获取规则。前台遇到已有任务时，可以在自身总预算内短暂复用；若坚持独立生成，则应明确允许重复请求，并规定写入归属，不能把它称为全局去重。

缓存使用临时文件后原子替换；用任务标识或生成代次阻止旧任务覆盖显式刷新结果。补充失效锁回收、每 worktree 的并发上限、缓存容量/过期清理，以及卸载时尚在运行的任务不得重新创建缓存的规则。

具体去抖窗口可以后定，资源上限和结果发布规则不能只留给实现临时决定。“不延迟 git add”也应改成“不等待模型完成，并满足可测量的启动开销预算”。

**验收**：预热未完成即提交、同 key 同时触发、连续不同 tree 暂存、任务崩溃、强制刷新与旧任务竞速、卸载期间任务完成均有稳定结果。

### R08 — 缓存键应覆盖实际生效的生成输入

**依据**：[design D5][design]（L134–144）以 tree 和 profile 等字段组成 key；[生成规格][generation-spec]（L93–100）又要求从历史推断风格；[后端规格][adapter-spec]（L80–98）支持本机 profile 和共享格式规范。

**影响**：`profileId` 不等于 profile 内容；同一名称可以改用另一 harness/provider。`configVersion` 也没有说明是配置格式版本、人工递增值，还是实际配置内容摘要。相同 base tree 还可能来自不同提交历史，导致风格输入不同但 key 相同。

**建议**：保留 tree 为内容身份，另对规范化的有效 profile、语言、格式规则、预算、排除规则和提示模板计算摘要。历史确实进入生成输入时，应纳入历史样本/风格结果摘要，或者明确接受这种变化不会立即刷新旧候选。不要对用户显示用的原始 diff 文本做缓存身份判断。

缓存条目记录实际生成后端、schema 版本和候选；读取时重新校验。fallback 的结果是按主 profile 的生成策略复用，还是按实际 fallback profile 存储，也应写明。涉及密钥的字段不得原样落入缓存。

`-a` 和路径提交并非必然不命中；只要 base/target tree 与全部有效参数相同，就应可以复用。临时 index 的路径不同不能单独成为失效理由。

**验收**：同名 profile 更换 provider、修改语言/排除清单、改变历史样本、fallback 成功、缓存损坏和同 tree 的不同提交入口都有明确命中结果。

### R09 — 补齐差异采集的确定性和敏感内容边界

**依据**：[生成规格][generation-spec]（L10–50）要求只从快照采集输入、排除秘密且不发送二进制内容；[design D5][design]（L123–132）承认 diff 受用户配置影响，但没有给出采集参数约束。

**核实结果**：Git 支持外部 diff driver 和 textconv；`git diff` 默认允许 textconv。因此“使用参数数组”和“比较两个 tree”并不能单独保证采集过程没有额外程序参与。来源：[Git 差异选项文档](https://git-scm.com/docs/git-diff#Documentation/git-diff.txt---no-ext-diff)。

**建议**：为采集路径固定差异格式及影响覆盖范围的参数，显式禁用 external diff 和 textconv；文件清单使用 NUL 分隔，不靠逐行拆路径。文件名作为参数传入时仍需避免被解释为 Git pathspec 模式。必要的 Git 环境继续保留，不能因安全处理丢失有效 index。

秘密排除应在构造模型 payload 前完成，并检查重命名/复制的源路径与目标路径。例如 `.env → notes.txt` 不能只检查新路径后就发送旧秘密内容。删除文件的旧内容同样适用。二进制、LFS 指针和 submodule 的统计/内容边界也应固定。

写入 tree 以及读取 index 的步骤还应验证是否会触发本工具的索引 hook，确保内部 Git 调用不会形成自触发循环。

**验收**：配置了会留下标记的 diff/textconv 程序时，采集不执行它们；特殊路径、敏感文件改名/删除、二进制和子模块不泄漏被排除内容；改变展示配置不影响应纳入的变化集合。

### R10 — 消息协议需要落到确定的解析和验收规则

**依据**：[Git 接入规格][git-spec]（L10–33、L80–92）、[生成规格][generation-spec]（L61–114）、[design D6/D9][design]（L146–163、L192–199）。

目前至少有六项需要明确：

1. **空提交的判定**：`--allow-empty` 只是允许 tree 不变，不意味着本次没有变化。应以 base/target tree 是否相等判断，而不是看到该选项就跳过有内容的提交。来源：[Git commit 文档](https://git-scm.com/docs/git-commit#Documentation/git-commit.txt---allow-empty)。
2. **模板与清理规则**：区分 `template` 来源、注释模板、实际用户正文、签名尾注和 scissors 区域；明确支持的 `core.commentChar`、`commit.cleanup` 及命令行覆盖场景。hook 没有获得全部原始命令行参数，不能只读取配置便宣称覆盖所有组合；无法判断时应保留原内容。
3. **完整输出 schema**：确定 type 枚举、scope 规则、字段空值、单行限制、正文条数/长度、控制字符和禁止伪造的尾注。补充明确的“证据不足，拒绝生成”结果，避免模型只能返回非法候选来表达失败。
4. **兜底解析边界**：移除外围代码围栏后仍必须得到完整合法的 JSON；不可把截断输出、普通文本或不完整 JSON 修剪成成功候选。过长内容应纠正或失败，不应通过盲目裁剪破坏原意。
5. **标题和风格优先级**：长度限制建议针对完整 header，包括 `type(scope)!: `。明确中文、英文、emoji、组合字符的计数范围；显示宽度约束与项目的字符串长度约束分别校验。仓库显式规范优先于历史推断，并说明是否真的支持无 conventional 前缀的风格。
6. **质量承诺范围**：design 声明不保证语义正确，spec 却要求一切无证据断言都被判定不合规。建议区分本地可以确定校验的格式/禁用字段，与依赖提示、评测和人工审阅的语义质量；不要把通用事实核验写成尚无实现手段的确定性保证。

**验收**：提供合法/非法候选与消息文件样例，覆盖模板、尾注、`-v/-vv`、显式消息、无前缀历史、超长标题、拒绝生成及截断输出。历史样本数量和输入字节预算固定，且历史语言不得覆盖配置语言。

### R11 — 安装与卸载需要按接入方式定义

**依据**：[proposal][proposal]（L59–60）承诺只写 hook 和缓存；[Git 接入规格][git-spec]（L122–138）要求自动追加到多种管理器且不覆盖生成文件。

**影响**：若集成需要修改管理器源配置或受版本控制的脚本，实际写入范围就超出 proposal 的描述。“追加一行”也未必能在已有 `exit`、转发逻辑和不同脚本语言中正确执行。

**建议**：为原生 hooks、已有手写 hook、各受支持管理器分别列出识别方法、写入目标、执行顺序、退出码传播、重复安装行为和卸载规则。需要修改管理器配置时，在 proposal 中准确列出这些文件；无法安全识别时报告冲突并提供接入指引。

根据 Git 解析出的有效路径定位 hooks 和每 worktree 的私有缓存，避免假设工作区 `.git` 一定是目录。Git 提供路径解析选项处理 gitfile 和路径重定位。来源：[Git 路径查询文档](https://git-scm.com/docs/git-rev-parse#Documentation/git-rev-parse.txt---git-pathltpathgt)。

卸载要识别本工具拥有的片段；安装后被用户修改的内容不能整文件回滚。还要声明 hook 是否跨 worktree 共享，避免在一个 worktree 卸载时意外影响其他使用者。

**验收**：重复安装、重复卸载、已有 hook 失败、安装后用户编辑、相对/绝对 `core.hooksPath`、linked worktree 和 GUI 环境都保持预期行为。

第一版只自动支持原生 hooks、对管理器提供指引，是可降低范围的选择；它不等同于已经满足现有自动集成规格，采纳时需要同步缩减规格。

### R12 — 补充版本、性能和交付依据

**依据**：[design][design]（L3–10、L25–41、L201–215、L266–282）引用未随仓库提供的桌面稿与本机实测，并将约 120ms 作为缓存命中体验；Windows 与去抖仍属于开放问题。

**影响**：目前无法复核参数适配与性能结论，也没有明确的第一版完成标准。已安装某个 harness 不应替代对实际 Node 可执行文件及版本的检查。

**建议**：

- 固定第一版操作系统、Git/Node 最低版本和各 CLI 的受支持版本/能力要求。
- 保留可复现的无敏感信息测量说明：命令、版本、输入规模、计时边界、样本数和失败情况；补入桌面稿或将必要论据直接整合到 design。
- 将 120ms 表述为当前设计依据或目标，分别测量 hook 启动、缓存命中、同步生成及“暂存后立即提交”；不要从空 Node 进程时间推导完整程序的性能保证。
- 固定总超时和全流程调用上限。一次格式纠正、一次 fallback、一次快照重试不能各自重置预算，形成超出用户预期的多轮等待。
- 完成上述决策后再补 `tasks.md`，让每项任务包含对应验收方法。

**验收**：新环境能按记录复现能力检测；不兼容后端被明确报告；缓存命中与未命中都有可测量指标；持续失败与重试仍受同一总预算限制。

## 5. 建议的修订与交付顺序

以下是实施顺序建议，不代表本次评审已经改变现有 OpenSpec 范围。

1. **先统一契约**：修正 R01 的参数定义；解决 fallback、fail-open 和严格模式范围；固定第一版平台与配置优先级。
2. **完成最小同步闭环**：有效 index 快照、受控输入、schema/renderer、消息保留、明确退出语义、`preview`/`doctor` 和原生 hooks 安装/卸载。先用 fake adapter 和一个受支持真实后端验通，再扩展其余后端。
3. **验证后端隔离并扩展覆盖**：逐版本补齐能力与传输样例，落实用户配置的 fallback；如交付严格模式，在这一阶段把第三个 hook 纳入完整安装和测试。
4. **交付预热缓存**：先确定启用语义与资源预算，再实现事件触发、并发任务、缓存发布和清理。预热可保持本次变更的第二阶段，也可以拆为独立变更；若拆出，必须同步移出本次 proposal/specs 的承诺。
5. **按需求增加管理器与平台支持**：每种接入方式有专门验收。只有明确交付的能力才写入第一版“支持列表”。

## 6. 最小验收清单

| 验收领域 | 至少覆盖的场景 | 主要断言 |
| --- | --- | --- |
| 提交内容 | 普通暂存、部分暂存、`-a`、路径提交、首次提交 | 输入来源与目标 tree 一致 |
| 消息保留 | `-m/-F/-c/-C/--amend`、fixup/squash、特殊 Git 操作 | commit 阶段不生成，不覆盖已有消息 |
| 消息文件 | 签名、模板、注释、cleanup、scissors、`-v/-vv` | 保留人工文字和尾注，不误解析 diff |
| 错误语义 | 不存在/未认证/超额/超时/非法输出、无编辑器、取消 | 退出码符合 R03，原文件不被失败结果污染 |
| 输入边界 | 特殊文件名、秘密文件改名/删除、二进制、textconv、submodule | 被排除内容不发送，采集不执行外部转换 |
| 后端适配 | 各种传输格式、缺少完成事件、插件/MCP、会话持久化 | 所有成功路径都经过同一校验与隔离要求 |
| 预热缓存 | 关闭开关、未完成即提交、连续暂存、刷新竞速、失效锁 | 成本有界、结果不串用、旧任务不覆盖新结果 |
| 一致性 | 生成期间变化、编辑后变化、后续 hook 变化、取消后重试 | 不发布已识别失效的候选，保留用户文字 |
| 安装维护 | 重复安装/卸载、已有 hook、管理器、worktree、GUI PATH | 安装范围准确，不破坏用户执行链 |
| 性能预算 | 命中、未命中、立即提交、多次失败 | 总时限和资源上限可验证 |

## 7. 相比上一轮意见的校正

- `post-index-change` 的问题不只是跨平台不确定性：第二参数的通用“索引变化”解释本身需要更正，证据见 R01。
- 第三个 hook 不是所有使用模式都必须安装；保留严格一致性功能时，需要把它纳入显式范围，并说明绕过与竞态边界，见 R04。
- “预热未完成便独立同步生成”会产生同 key 的重复请求，现有后台去重要求不能覆盖它，见 R07。
- 临时 index 不意味着缓存必然失效；决定因素是快照和有效生成参数是否相同，见 R08。
- 默认关闭预热、减少首批 adapter、暂缓管理器自动集成，属于范围建议；fallback 默认行为矛盾、fail-open 矛盾和参数语义错误属于应修订的问题，不能混为一类。
