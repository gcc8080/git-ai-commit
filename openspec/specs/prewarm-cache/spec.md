# prewarm-cache Specification

## Purpose

定义可选的提前生成与结果复用：预热如何被启用与授权、显式消息与预热的边界、何时被触发与过滤、发送前如何复核、后台与前台任务如何
协调、缓存条目由什么决定、结果如何发布与清理，以及预热失效时系统如何退回同步生成而不改变其他行为。

## Requirements

### Requirement: 预热需在本机显式开启，并在执行时确认授权

预热 MUST 默认关闭，只能由用户在本机配置中显式开启。仓库共享配置 MUST NOT 开启预热。用户首次开启时，系统 MUST 告知：数据会在
暂存阶段发送至后端。授权 MUST 以执行时读到的本机配置为准：每次触发时、以及后台任务实际发送之前，系统 MUST 读取当前有效的配置，
只有明确开启才继续。hook 是否已安装 MUST NOT 被当作授权依据；关闭 MUST 立即生效，不依赖重新安装或重启任何进程。已发出的请求
不可撤回。

#### Scenario: 未开启预热
- **WHEN** 用户未开启预热，并执行 `git add`
- **THEN** 后端调用次数为零

#### Scenario: 直接修改配置关闭预热
- **WHEN** 用户开启预热并完成安装，之后直接把本机配置改为关闭，不重新安装，也不重启任何进程
- **THEN** 随后的暂存操作不启动任何预热请求

#### Scenario: 关闭时已有任务在等待
- **WHEN** 用户关闭预热时，某个预热任务仍在等待去抖窗口、尚未发送
- **THEN** 该任务在发送前放弃，不发送请求

#### Scenario: 共享配置试图开启预热
- **WHEN** 仓库共享配置中出现开启预热的设置
- **THEN** 系统拒绝该设置，预热保持关闭

#### Scenario: 首次开启预热
- **WHEN** 用户在安装过程中选择开启预热
- **THEN** 系统说明暂存阶段即会发送差异内容，此后改用显式消息或跳过开关都无法撤回已发出的请求

### Requirement: 关闭预热与卸载是两项操作

系统 SHALL 提供关闭预热的操作：设置本机配置，并移除预热所用的 hook。关闭预热 MUST NOT 移除消息准备阶段的 hook 与缓存。
卸载则移除本工具的全部 hook 与缓存。

#### Scenario: 关闭预热
- **WHEN** 用户执行关闭预热的操作
- **THEN** 预热 hook 被移除，提交时的生成与已有缓存照常可用

### Requirement: 显式消息与预热的边界

消息准备阶段对显式消息 MUST NOT 生成。开启预热时，提交命令自身对 index 的写入也会产生预热提示；系统 MUST NOT 承诺普通的显式消息
提交一定不产生预热请求，只保证：发送前复核发现快照已无差异时不发送；暂存阶段已为同一快照预热过时，不为它新增请求。单次跳过开关
MUST 保证其作用的 Git 命令不引发任何后端请求。系统 MUST NOT 宣称显式消息或跳过开关能够撤回此前已发出的预热请求。

#### Scenario: 暂存阶段已预热，随后显式提交
- **WHEN** 预热已开启，用户执行 `git add`（预热已为该快照发起请求），再执行 `git commit -m "..."`
- **THEN** 暂存阶段的请求照常发生，提交阶段不为同一快照新增请求

#### Scenario: 提交在去抖窗口内完成
- **WHEN** 预热已开启、暂存阶段未预热，用户执行 `git commit -m "..."`，且提交在去抖窗口内完成
- **THEN** 由该提交触发的预热任务在发送前发现快照已无差异，不发送请求

#### Scenario: 需要确定不外发
- **WHEN** 预热已开启，用户启用单次跳过开关执行 `git commit -m "..."`
- **THEN** 无论提交耗时多久，该命令都不引发任何后端请求

### Requirement: 触发与过滤

系统 SHALL 把索引写入视为"暂存内容可能已变化"的提示，MUST NOT 依赖 hook 参数判断是否为暂存操作。收到提示后，系统 MUST 依次过滤：
启用了单次跳过开关或带有内部重入标记时，不继续；执行时读到的本机配置未开启预热时，不继续；仓库处于 merge、rebase、cherry-pick、
revert 等流程中时，不继续；暂存区与 HEAD 无差异时，不继续。过滤中的差异检查 MUST NOT 执行外部 diff 程序或 textconv 转换；
检查出错或无法判断时，MUST 视为不预热，MUST NOT 视为发现变化。过滤阶段 MUST NOT 调用后端。

#### Scenario: 暂存文件
- **WHEN** 预热已开启，用户执行 `git add`，暂存区因此与 HEAD 产生差异
- **THEN** 系统在后台启动预热任务

#### Scenario: 通过其他客户端暂存
- **WHEN** 用户通过调用原生 Git 的 IDE、终端 UI 或编码 agent 暂存文件
- **THEN** 预热同样被触发，无需任何 shell 配置

#### Scenario: 配置了 textconv 或外部 diff
- **WHEN** 仓库为暂存的文件配置了 textconv 转换程序或受信任的外部 diff 程序，且该转换会让新旧内容看起来相同
- **THEN** 过滤阶段不执行这些程序，并正确识别出暂存区确有变化

#### Scenario: 只刷新了文件状态
- **WHEN** 暂存区为空时，某个状态查询刷新并写入了 index
- **THEN** 系统不启动预热任务

#### Scenario: 本工具自身写入 index
- **WHEN** 本工具在生成过程中执行了会写入 index 的 git 命令
- **THEN** 由此触发的提示被过滤，不启动新的预热任务

#### Scenario: 合并过程中暂存
- **WHEN** 用户在解决合并冲突时暂存文件
- **THEN** 系统不启动预热任务

#### Scenario: 仓库还没有任何提交
- **WHEN** 用户在尚无 HEAD 的仓库中暂存文件
- **THEN** 系统不启动预热任务，首次提交时按同步路径生成

#### Scenario: 不执行 hook 的客户端
- **WHEN** 用户通过不执行 Git hook 的客户端暂存文件
- **THEN** 不发生预热，提交时系统按同步路径生成

### Requirement: 不阻塞触发它的 Git 命令

预热任务 MUST 在后台执行，触发它的 Git 命令 MUST NOT 等待模型完成。过滤 MUST 在不启动本工具主程序的前提下完成，被过滤掉的触发
MUST NOT 启动主程序。过滤阶段带来的同步开销 MUST 有可测量的上限。预热过程中的任何失败 MUST NOT 产生用户可见的输出，MUST NOT
影响该 Git 命令的退出码。

#### Scenario: 暂存大量文件
- **WHEN** 用户执行 `git add` 暂存大量文件，预热随之启动
- **THEN** `git add` 的额外耗时不超过过滤阶段的开销上限，不等待生成完成

#### Scenario: 被过滤的触发
- **WHEN** 预热关闭、启用了跳过开关、带有重入标记、处于特殊 Git 流程或暂存区为空时发生索引写入
- **THEN** 本工具主程序的启动次数为零

#### Scenario: 预热失败
- **WHEN** 后台预热因后端不可用而失败
- **THEN** 用户在暂存时看不到任何错误输出，`git add` 的退出码不变

### Requirement: 发送前复核

后台任务在去抖窗口结束、实际发送之前，MUST 重新确认授权、跳过条件与特殊流程，并重新计算快照。授权已关闭、条件已命中、或快照
与 HEAD 已无差异时，MUST NOT 发送。该复核只决定尚未发出的预热请求是否发送，MUST NOT 被用于否定提交阶段捕获的快照或候选。

#### Scenario: 等待期间撤回了暂存
- **WHEN** 预热任务在等待去抖窗口期间，用户撤回了全部暂存
- **THEN** 该任务不发送请求

#### Scenario: 等待期间提交已完成
- **WHEN** 预热任务在等待去抖窗口期间，触发它的提交已经完成
- **THEN** 该任务发现快照已无差异，不发送请求

### Requirement: 每个缓存键的任务状态

每个缓存键 MUST 处于且只处于以下状态之一：不存在、生成中、就绪、失败。取得生成权 MUST 是原子的；同一个键在同一时刻 MUST 至多
有一个生成在进行，这一约束同样适用于异常恢复与强制刷新。释放生成权时，任务 MUST 确认它仍属于自己（同一进程、同一代次）；旧代次的
任务 MUST NOT 释放新代次的生成权。提交时发现同一个键正在由后台生成，系统 MUST 在自身的总时间预算内等待该任务，MUST NOT 为同一个
键再发一次请求。

取代现有持有者之前（包括回收超出时限的生成权、强制刷新），系统 MUST 核对持有者身份，并确认旧持有者及其后端子进程都已退出；
身份核对 MUST 防止误把被复用的进程号当作旧持有者。无法确认退出时，系统 MUST NOT 取代旧持有者，也 MUST NOT 仅因超出时限就为同一个
键启动新的生成。

#### Scenario: 同一个键被并发触发
- **WHEN** 同一份暂存内容在短时间内多次触发预热
- **THEN** 只有一个任务向后端发起请求

#### Scenario: 预热未完成时提交
- **WHEN** 用户在预热任务完成前执行 `git commit`，且本次提交的快照与该任务相同
- **THEN** 系统在总时间预算内等待该任务的结果，不重复发起请求

#### Scenario: 预热任务崩溃
- **WHEN** 某个预热任务在生成中途异常终止，其进程已不存在
- **THEN** 其遗留的生成中状态被识别为失效，之后的触发或提交可以重新取得生成权

#### Scenario: 超出时限但旧持有者仍存活
- **WHEN** 某个键的生成权已超出时限，但旧持有者被暂停，或其后端子进程仍在运行
- **THEN** 系统先终止并确认旧持有者及其后端子进程都已退出，然后才开始新的生成；任一时刻该键至多只有一个生成在进行

#### Scenario: 无法确认旧持有者退出
- **WHEN** 系统无法确认旧持有者已经退出
- **THEN** 系统不为该键启动新的生成；提交阶段在剩余预算内等待，或按生成失败的规则处理

#### Scenario: 进程号已被复用
- **WHEN** 旧持有者已退出，其进程号被一个无关进程复用
- **THEN** 系统不向该无关进程发送任何信号，并将旧的生成权视为失效

#### Scenario: 旧任务在刷新之后才清理
- **WHEN** 用户对某个键强制刷新，旧代次的任务晚于新任务取得生成权之后才退出并清理
- **THEN** 旧任务的清理不释放新代次的生成权

### Requirement: 每个 worktree 的后台并发上限

同一个 worktree 中，后台预热任务 MUST 至多一个在运行。新的触发对应不同的快照时，系统 MUST 以最新的快照为准，取消已过时的任务；
在一个短暂的去抖窗口内连续发生的触发，MUST 只为最后的快照发起请求。提交阶段的生成不受此上限约束。

#### Scenario: 连续暂存
- **WHEN** 用户在几秒内连续执行三次 `git add`，产生三个不同的快照
- **THEN** 任一时刻至多有一个后台任务在运行，最终只有最新快照得到生成结果

### Requirement: 结果的原子发布与代次

缓存结果 MUST 以原子方式发布，读取方 MUST NOT 读到部分写入的结果。发布前，任务 MUST 确认该键的当前代次仍等于自己的代次，不一致时
MUST 丢弃结果。强制刷新 MUST 使同一个键上旧的在途任务失效：旧任务完成时 MUST NOT 覆盖刷新后的结果。

#### Scenario: 强制刷新与旧任务竞速
- **WHEN** 用户对某个键强制刷新，而该键此前的预热任务在刷新完成后才结束
- **THEN** 缓存中保留的是刷新后的结果

### Requirement: 缓存键覆盖全部有效生成输入

缓存键 MUST 由基准快照、目标快照，以及规范化后的有效生成参数共同决定。这些参数包括：后端、供应商、模型、思考强度、后端版本、语言、
格式与长度规则、输入预算、排除清单、scope 规则、用于推断风格的历史样本、提示模板版本与 schema 版本。缓存键 MUST NOT 依赖差异的
文本表示，MUST NOT 依赖 profile 名称或配置文件的版本号，MUST NOT 只由分支名或文件清单构成。提交方式本身（普通提交、自动暂存提交、
限定路径提交）MUST NOT 影响缓存键。

#### Scenario: 改变差异显示配置
- **WHEN** 用户修改了影响差异文本呈现的 Git 配置，但暂存内容未变
- **THEN** 缓存仍然命中

#### Scenario: 同名 profile 更换供应商
- **WHEN** 用户保持 profile 名称不变，但将其供应商改为另一家
- **THEN** 缓存不命中，系统按新配置重新生成

#### Scenario: 修改语言或排除清单
- **WHEN** 用户修改了输出语言或秘密排除清单
- **THEN** 此前的缓存条目不再命中

#### Scenario: 历史样本变化
- **WHEN** 基准快照相同，但用于推断风格的历史样本不同
- **THEN** 缓存不命中

#### Scenario: 自动暂存提交的快照与预热时相同
- **WHEN** 所有修改都已暂存并完成预热，用户执行 `git commit -a`
- **THEN** 本次提交的快照与预热时相同，缓存命中

### Requirement: 缓存条目的内容与校验

缓存条目 MUST 记录实际产出结果的后端与模型、schema 版本与候选，MUST NOT 保存差异内容、prompt 原文或凭证。读取条目时，系统 MUST
按当前 schema 重新校验，校验失败或条目损坏时 MUST 视为未命中。由回退后端产出的结果 MUST 以主 profile 对应的缓存键存储，并标注
实际后端。

#### Scenario: 缓存条目损坏
- **WHEN** 某个缓存条目无法解析，或不符合当前 schema
- **THEN** 系统视为未命中，按同步路径生成

#### Scenario: 回退后端产出的结果
- **WHEN** 预热时首选后端失败，由回退后端产出结果，之后用户以同一主 profile 提交
- **THEN** 缓存命中，诊断中可以看到实际产出结果的后端

### Requirement: 命中时直接使用

提交时缓存命中的，系统 MUST 直接使用缓存中的候选，MUST NOT 重新发起生成。

#### Scenario: 常规提交命中预热结果
- **WHEN** 用户暂存后执行 `git commit`，且暂存内容自预热以来未变
- **THEN** 消息立即填入，编辑器几乎无等待地打开

### Requirement: 未命中时退回同步生成

缓存未命中、或对应条目处于失败状态时，系统 MUST 在提交流程中同步生成，并在等待期间提供进度提示。系统 MUST NOT 使用基于其他快照
或其他生成参数的缓存条目。

#### Scenario: 暂存后又修改了内容
- **WHEN** 用户在预热完成后又暂存了新的修改，然后执行 `git commit`
- **THEN** 缓存不命中，系统为当前快照同步生成，并在等待期间显示进度

#### Scenario: 预热曾经失败
- **WHEN** 对应条目处于失败状态
- **THEN** 系统在提交时尝试一次同步生成

### Requirement: 缓存作用域、容量、卸载与清理

缓存与任务状态 MUST 存放在各 worktree 私有的 Git 目录中，并按安装区分：每次安装有独立的安装身份与状态目录。状态 MUST NOT 跨
worktree、跨仓库或跨安装共享；不同 worktree 的锁 MUST 互相独立。缓存条目数与保留时间 MUST 有上限，超出时 MUST 被清理。

后台任务 MUST 从启动起就能被卸载发现和终止，包括仍在等待去抖窗口、尚未取得生成权的任务；后台任务 MUST NOT 创建状态目录。卸载时，
系统 MUST 先使本次安装的状态目录对所有任务失效，再终止全部在途任务并确认退出，最后移除目录。卸载之后，尚未发出的预热请求 MUST NOT
再被发出，状态目录 MUST NOT 被重建。卸载后重新安装时，此前安装的任务 MUST NOT 进入新安装的状态目录，也 MUST NOT 发布结果。
卸载 MUST NOT 被描述为能够撤回已经发出的请求。

#### Scenario: 多个 worktree
- **WHEN** 同一仓库的两个 worktree 同时使用本工具
- **THEN** 两者的缓存与锁互不干扰

#### Scenario: 卸载时有任务在等待去抖窗口
- **WHEN** 某个预热任务已经启动、仍在等待去抖窗口，此时用户执行卸载
- **THEN** 该任务不发出请求，状态目录不被重建

#### Scenario: 卸载时有任务正在生成
- **WHEN** 某个预热任务正在生成时，用户执行卸载
- **THEN** 该任务被终止并确认退出，其结果不被发布，状态目录不被重建

#### Scenario: 卸载后立即重新安装
- **WHEN** 用户卸载后立即重新安装，此前安装的某个任务随后恢复运行
- **THEN** 该任务不能进入新安装的状态目录，也不能发布结果

### Requirement: 强制刷新

系统 SHALL 提供显式忽略缓存、重新生成的方式。

#### Scenario: 对结果不满意
- **WHEN** 用户请求强制刷新
- **THEN** 系统忽略现有缓存条目重新生成，并以新结果替换该条目
